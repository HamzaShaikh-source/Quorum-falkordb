# Audit remediation record

Baseline: `a2cc69dd34035f7900bf0071a0f697e5f885f29a` (`origin/main`). Local branch: `codex/audit-remediation`. Work has not been pushed, merged, or deployed. The original `hamza/frontend` branch was clean and is preserved.

## Findings and implementation

1. **Private actions and derived context.** REST action listing, execution, staging, corrections, handoff listing/claim/review, blast reports, brain traces and prompt diffs now apply the same current workspace viewer used by MCP retrieval. Hidden IDs return non-disclosing failures. Derived nodes retain every private parent scope: a viewer must satisfy all of them. Common facts can still support private facts; private corroboration cannot silently broaden access. Contradiction checks do not inspect scopes the new assertion cannot disclose. Private correction alerts inherit action scopes. Configured service tokens remain unscoped.
2. **Live access and audit records.** SSE validates the bearer token again during replay, delivery and heartbeat, and rebuilds linked-team access on delivery. Revoked streams close. Node, edge, action, correction, handoff and audit events are filtered. Unknown event categories fail closed for members. Audit records retain conservative scope metadata; historical records without that provenance and raw Cypher logs are restricted to service callers. This deliberately favors privacy over showing incomplete historical evidence to members.
3. **ID collisions.** Creation cannot replace an existing node of any kind. Atomic process locks select one winner for concurrent creates. Exact fact retries and unchanged derivation/staging retries reuse existing state without adding edges, rerunning gates, resetting quarantine or dispatching actions. Changed content, cross-kind reuse and inaccessible IDs fail. Observed fact IDs include member/scope namespaces; duplicate detection considers only visible facts. New causal self-links are rejected; external derivation cannot reuse an existing ID to create a cycle.
4. **Durable compensation.** A single `MERGE (s:QCheckpoint {id:'state'}) SET s.json=$json` stores the authoritative nodes, compensation intent, epoch, execution intent, stable keys, handoffs, workspace and call/agent state. Existing typed graph nodes and edges remain replayable projections. Those projection writes are independent statements, not a transaction. Projection failures still fail the request. Recovery loads the checkpoint and repairs projections, including deletions. A proposed chained-MERGE diff failed a real FalkorDB regression test and was discarded.
5. **Worker recovery.** Compensation claims persist an owner, expiring lease, attempt count and retry schedule before delivery. Claims are fenced per attempt. Expired and historical lease-less dispatches recover. Exhaustion records a failure and creates a human escalation. The application lifecycle starts/stops the worker and discovers persisted tenants after restart. External HTTP runs outside graph locks. Uncertain executions retry with their durable key after lease expiry; exhausted reconciliation escalates rather than claiming delivery. Correctness requires provider idempotency and compensation tombstones.
6. **External service and corrections.** A configured `HELPDESK_URL` selects the real HTTP adapter, with bounded timeouts, explicit HTTP failures and a stable tenant-scoped idempotency key. Development mocks remain explicit; production cannot silently claim mock success. REST/MCP staging accepts optional action payloads, which are sent to the adapter and used for correction recipients and subjects. Corrections use actual action content, relevant healthy root facts and source IDs. Missing recipient or verified facts produces `NEEDS_HUMAN_INPUT`. Approval produces `APPROVED_PENDING_DELIVERY`; there is no correction-delivery integration, so neither backend nor UI claims the message was sent. Demo reset does not reset an HTTP provider and gives replayed demo actions a fresh run namespace.
7. **Authentication and credential hygiene.** Production ignores `ALLOW_DYNAMIC_TOKENS=true`. Explicitly configured tokens, issued member credentials, expiry, rotation and revocation remain supported. `/api/dev-config` requires a development demo and exposes only built-in sandbox credentials, never configured service secrets. No public credential-bearing `config.json` existed; none was created. The browser no longer loads bearer secrets from public configuration. The switcher labels preloaded demo credentials only in a sandbox. Docker contexts exclude secrets and local environments.
8. **Ranking.** A mutation-aware healthy fact index supplies full retrieval candidates. Status, stale flags, ingestion, superseding, restore, replacement, deletion and restart update membership. Current viewer checks remain mandatory. Original insertion order is retained for equal-score candidates. A bounded, revision/viewer keyed cache avoids recomputing historical comparison evidence for repeated queries. The compact context/preview path still scans historical data for short IDs, provenance and evidence comparisons; it is measured separately and is not advertised as indexed full retrieval. Existing embedding-cache eviction now enforces a reduced cap even when the cache was already larger.
9. **UI polish.** Existing computed cursor radii, interactive-ancestor lookup, keyboard/reduced-motion behavior and clipping on numbered items were retained and browser-tested. Navigation has one CSS tooltip label for hover/focus, descriptive names and titles, and a scrollable narrow rail with focus reachability. A 1280px overflow discovered during QA was corrected. Reset clears stale containment selection and resyncs the graph. Timing badges distinguish real FalkorDB execution, failures, in-process operations and historical illustrative statements; server execution time is used when supplied by the driver, without rounding every fast operation to zero.
10. **Claims and setup.** README and setup/security notes describe the single-writer deployment and recovery checkpoint. Standalone persisted MCP writers are refused; stdio clients use the bridge to embedded MCP. Compose defaults to an empty workspace (`QUORUM_DEMO=0`) and production forces demo off. Historical benchmark artifacts are retained. New measurements have their own artifacts and explicit boundaries. An unused `python-jose` dependency and its vulnerable ECDSA dependency chain were removed after confirming there are no imports.

## Actual production boundaries

- Execution: REST/MCP authorization → process-locked `execute_guard` → durable checkpoint and projections → HTTP adapter outside the lock → durable confirmation. A failed persistence call does not return successful execution.
- Quarantine: authorized root → locked causal BFS → quarantine/epoch plus compensation or correction intent → atomic checkpoint → replayable projections. The console does not describe that BFS as a FalkorDB traversal query.
- Handoff claims: current visibility and role → one shared graph/handoff lock → lease transition → persistence before successful API/MCP response.
- Recovery: reload authoritative checkpoint → rebuild candidate index and valid embedding cache → repair projections → recover expired work with the original provider key.

## Storage transition and deployment limits

Existing graphs without a checkpoint load through the original QNode/QHandoff/QMeta format. The next successful sync adds the checkpoint; it does not delete historical data or require a destructive migration. Legacy executed actions retain their historical external key. New actions use tenant-scoped keys. New model fields have defaults for historical records.

Use one backend writer with embedded MCP. Process locks are not distributed locks. Multiple API writers and standalone persisted MCP are unsupported. A database acknowledgement is durability to FalkorDB, not a promise that the database's own disk/AOF/replication policy survives every host failure. Configure database durability and backups for deployment needs.

Before downgrading to an older writer, stop writers, load and successfully commit every tenant with this version so projections match the checkpoint, and take a database backup. Remove that tenant's QCheckpoint only as part of the deliberate downgrade, then start the older writer. Do not run an older writer alongside this version or later reuse a stale checkpoint. No downgrade or destructive migration was executed during this task.

Compensation can only be as strong as the external provider's idempotency/tombstone contract. A crash after external success is reconciled by replaying the same key; exhausted retries require a human. Correction approval is intentionally separate from confirmed delivery. Payloads and replacement facts must be supplied rather than invented.

## Regression evidence

`test_remediation.py` covers production override conflicts, real member-token isolation, linked access, mixed private scopes, overwrites, concurrent creates, harmless retries and revocation of an already-open stream. `test_recovery_remediation.py` covers expired/concurrent leases, retry schedules and exhaustion, persistence failure before external execution, replay after uncertain external success, candidate invalidation/tie order, generic correction provenance, a real local HTTP fake service, and HTTP-provider-safe demo reset.

`test_persistence.py` adds real FalkorDB checkpoint/quarantine recovery, external success followed by confirmation failure, and checkpoint success followed by projection failure. Existing scenario/correction tests now assert pending delivery and missing-input behavior instead of fabricated recipients and dispatched messages. Existing route tests now authenticate SSE realistically and assert hidden/missing-ID failures. The context comparison test checks measured baselines without assuming a universal ordering between prose and top-eight JSON. The browser interaction test checks scroll/focus reachability instead of requiring ten controls to fit simultaneously on a phone.

## Verification and measurements

Final command results, counts, coverage, performance numbers and browser results are recorded in the accompanying completion report and `audit-evidence/` artifacts. Historical failed attempts are retained as development evidence; they are not passing results.

The untouched Linux baseline passed **236 backend tests** against real FalkorDB. The first global Windows run had a broken pytest plugin/MCP environment. Two Python 3.13 Windows stress runs stalled in event-loop socket setup; their stack evidence was saved and they were stopped. Final backend verification uses Linux with Python 3.12, matching CI. Windows Python 3.12 also passed the targeted real-database affected checks.

Dependency audits: backend requirements and frontend production dependencies report no known vulnerabilities. The complete frontend audit also reports **7 development-tool findings: 3 critical, 1 high, 3 moderate** in Vitest/coverage/tinypool/mocker/vite-node/Vite/esbuild. npm proposes major Vitest/Vite upgrades. Those upgrades were not performed because the brief explicitly excludes dependency upgrades; the advisory details and fix ranges are retained in `audit-evidence/npm-audit-all.json`. These findings are not represented as a clean all-dependency audit.
